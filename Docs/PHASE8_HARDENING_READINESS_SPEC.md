# Phase 8 Build Specification — Security, Resilience and Pilot Readiness

**Implements:** T80–T84  
**Prerequisite:** functional Phases 1–7 complete and green.  
**Outcome:** evidence-backed readiness assessment for a synthetic-data pilot and a controlled route to production onboarding. This phase does not authorise real-data ingestion or claim ISO certification.

## 0. Fixed decisions

- Phase 8 is a release gate and remediation phase, not a feature shortcut.
- Synthetic data remains mandatory until a separately approved onboarding plan.
- No unresolved P0/P1 tenant-isolation or security issue is accepted for pilot release.
- Accessibility includes manual critical-flow testing, not automated scanning alone.
- Backup claims require a completed restore exercise.
- ISO/legal review remains licensed and human; readiness is not certification.

## 1. Release gates

No production EMS pilot until all gates have named owners, dated evidence and accepted residual risks:

1. Tenant isolation and authorisation.
2. Audit/record integrity and retention.
3. Privacy/data protection.
4. Accessibility/usability.
5. Performance/reliability/observability.
6. Backup, restore and disaster recovery.
7. Secure development/dependency/supply chain.
8. Legal-content source fitness and competent review process.
9. Licensed ISO 14001:2026 requirement mapping.
10. Operational ownership/support/training.
11. Separate real-data onboarding approval.

## 2. Threat model scope

Actors: unauthenticated attacker, ordinary member, site-scoped user, privileged organisation user, malicious/compromised tenant user, suspended user with live session, platform operator, background worker, compromised AI/provider response and accidental administrator.

Assets: tenant records, environmental/legal/incident/person data, evidence bytes, credentials/tokens, immutable approvals/reports, audit history, legal sync provenance, carbon/LCA calculation integrity and availability.

Trust boundaries: browser/server, NextAuth/session, server actions/API routes, application/Neon pooler, runtime/migration DB roles, worker/outbox, object storage, OpenRouter, legal providers, exports/downloads and deployment/preview environments.

Required abuse cases include IDOR, mixed-tenant foreign keys, mass assignment, stale permission, CSRF/action replay, unsafe file upload/download, export injection, prompt injection, job replay, cursor poisoning, audit tampering, RLS context leakage, cache-key collision, log leakage, denial of service and privileged configuration misuse.

## 3. T80 cross-tenant adversarial suite

Use `PHASE1_ADVERSARIAL_TEST_MATRIX.md` plus every phase-specific test section. Build a machine-readable resource/endpoint registry so adding a new customer-owned route without an isolation test fails CI.

Required harness:

- two synthetic Organisations with overlapping human-readable names;
- ordinary, scoped, dual-member, privileged, suspended and unauthenticated actors;
- helper to run the same list/detail/create/update/delete/transition/export/download assertions per resource;
- mixed-parent ID generator;
- response-body/header/filename leak assertions;
- aggregate invariance: adding B data never changes A result;
- job and AI context assertions; and
- optional RLS integration suite against disposable Neon branch/local Postgres.

Gate: zero open P0/P1 tenant-isolation findings. Any exception requires owner, expiry and compensating control; broad test exclusions are prohibited.

## 4. T81 audit, retention and export

Create a record-classification matrix:

| Class | Examples | Required policy fields |
|---|---|---|
| Immutable issued | reports, obligation approvals, audit reports, review packs/minutes | retention, hold, successor/addendum, export |
| Operational controlled | aspects, controls, objectives, NC/CAPA | retention trigger, archive, correction history |
| Evidence | invoices, certificates, photos, source payloads | classification, licence, checksum, scan, retention, hold |
| Personal/restricted | competence, restricted incidents | access purpose, retention, subject request/export restrictions |
| Telemetry/audit | app audit, AI interaction metadata, job logs | minimum content, retention, integrity, access |

Implement retention as preview → approval → queued execution → deletion/tombstone event. Preview reports IDs/counts/classes only to authorised users. Holds always win. Issued/approved records use archival/anonymisation rules, not silent hard delete.

Organisation export requirements:

- manifest with schema/export version, organisation, generated by/time, record counts/checksums;
- structured JSON/CSV plus referenced evidence where authorised;
- exact source/version links and audit events;
- no platform secrets, other tenants, password/auth tokens or unlicensed provider content;
- resumable generation for large exports; expiry and access logging; and
- restore/import is a separately validated administrative operation, never assumed from export.

## 5. T82 accessibility and usability

Target WCAG 2.2 AA unless owner approves another standard. Test keyboard-only, screen reader names/relationships, focus order/return, headings/landmarks, contrast, zoom/reflow, error summary/field association, timeout/session messaging, tables, charts, dialogs, menus, file upload, print/PDF and status without colour alone.

Critical flows:

- organisation switch and role administration;
- aspect assessment/significance explanation;
- legal candidate → applicability → obligation approval;
- objective/action update;
- audit execution/finding/report;
- incident/NC/CAPA/effectiveness closure;
- competence evidence/expiry;
- management-review pack/minutes; and
- evidence/report downloads.

Automated scanning supplements manual assistive-technology review. Gate: no critical/blocking accessibility issues in critical flows; remaining issues owned and dated.

## 6. T83 performance, resilience and operations

Define SLOs before load testing. Suggested starting measures (targets require owner approval): page/API latency percentiles, export completion, scheduled-job freshness, legal cursor staleness, notification delay, error rate and restore objectives.

Synthetic scale profiles must include multiple tenants, sites, years of monitoring, thousands of obligations/actions/findings, evidence metadata, and legal events without real content.

Test:

- Neon pooled connection saturation/cold start/timeouts;
- N+1 and unbounded list/search/report queries;
- dashboard aggregate indexes;
- concurrent approval/transition optimistic locking;
- outbox backlog/retry/dead-letter/recovery;
- legal provider outage/rate limit/malformed payload;
- object-store outage and partial upload cleanup;
- large export/report generation;
- backup/PITR and full restore to isolated environment;
- migration expand/backfill/contract with rollback/roll-forward; and
- region/deployment failure according to selected architecture.

Observability:

- structured logs with correlation/organisation-safe identifiers and redaction;
- metrics for HTTP, DB, jobs, cursors, outbox, exports, storage and auth denials;
- alerts with runbook links;
- no environmental values, evidence text, personal certificate data, tokens or prompts in logs; and
- synthetic canaries for login, scoped read, job and download.

## 7. Secure development and supply chain

- dependency lockfile and automated vulnerability/licence scanning;
- secret scanning and no secrets in examples/tests;
- SAST and custom unscoped-Prisma/endpoint-registry checks;
- file upload validation, quarantine/scan interface and safe content disposition;
- CSV formula-injection protection; JSON/export size limits;
- security headers, CSP compatible with Next.js app, secure cookies and CSRF posture review;
- password/credential lifecycle review; production decision on SSO/MFA/reset/invitation;
- separation of runtime, migration and platform-job credentials;
- protected branches/reviews/migration approval; and
- incident response for tenant breach, legal-feed outage, corrupted calculation and lost evidence.

## 8. T84 licensed and competent review

Create configurable evidence mapping fields, then have authorised humans perform:

- licensed ISO 14001:2026 requirement-to-feature/process/evidence mapping;
- gap/owner/action/date tracking;
- competent legal review of source coverage, applicability method and evaluation cadence;
- certification-body independence check; and
- claims-language review to remove “ISO compliant/certified/legally complete” unless independently substantiated.

Repository may store clause identifiers and organisation-authored implementation notes, not copied standard text without licence permission.

## 9. Real-data onboarding boundary

Phase 8 ends with synthetic readiness. A separate onboarding plan must define:

- authorised datasets and purpose;
- data owner and lawful basis/privacy assessment;
- source-to-target mapping, validation and reconciliation;
- secure transfer and deletion of temporary copies;
- evidence/checksum and provenance;
- dry run, approval, rollback and sign-off;
- production support and incident plan; and
- explicit prohibition on placing real data in Claude/AI prompts unless separately governed.

## 11. Adversarial/readiness tests

- Full endpoint/resource registry has matching tenant tests.
- Runtime role cannot mutate audit events/issued records or disable RLS.
- Cache, search, aggregate, export, notifications and AI context remain isolated.
- CSV cells beginning `=`, `+`, `-`, `@` are safely exported.
- Malicious filename/MIME/oversize/duplicate/checksum mismatch fails safely.
- Retention preview and execution are idempotent; hold blocks execution.
- Export contains manifest/checksums and no foreign/platform-secret content.
- Backup restore reconciles schema version and synthetic record counts/checksums.
- Concurrent transitions permit one valid winner and clear conflict result.
- Provider/job outages recover without cursor loss/duplicate decisions.
- Logs/telemetry pass secret and representative sensitive-data scanning.
- Critical flows pass accessibility manual and automated checks.
- No production/real environmental data used in any hardening test.

## 13. Definition of done

All release gates have evidence and accepted owners; no P0/P1 tenant/security issue remains; restore and failure exercises pass; critical workflows are accessible; legal/ISO claims are human-reviewed; and the system is approved only for a synthetic pilot until a separate real-data onboarding decision.
